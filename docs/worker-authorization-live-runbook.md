## Инварианты и запреты

1. Production `main`, порт 8787, действующие OAuth-данные и профиль браузера не трогать до отдельного release gate.
2. Для теста использовать только отдельный Staging, **новую** тестовую Issue/задачу и новую уникальную browser-worker conversation в заранее выбранном ChatGPT Project. Существующий неопределённый ход `qa_report` не воспроизводить.
3. Сначала `devos_worker_probe` ровно один раз. Его nonce — не авторизация. Затем один `devos_noop` и ожидание результата; только `approved=true` открывает обычные инструменты и финальный `devos_worker_report`.
4. Локальная сторона выдаёт разрешение только при совпадении подписанного одноразового challenge, **реального MCP-сеанса и OAuth client**, точного сохранённого URL, worker ID/turn и активного task-lock. Никакие аргументы модели, текст ответа, похожий URL или роль «worker» не являются доказательством.
5. Провайдерская история должна быть получена из **HTTPS-источника того же ChatGPT origin**, по точному пути чата, ответом **GET HTTP 200** с структурированным результатом инструмента в пределах того же пользовательского хода. HTTP 401/404, POST, другой origin, неверная роль, отсутствующий родитель или противоречивые nonces означают **отказ**.
6. При `worker_proof_pending` или `authorization_required` у воркера: **не** показывать ему пароль владельца, не запрашивать `devos_authorize_chat`, не вызывать Mac-инструменты или `devos_worker_report` без разрешения. Записать точный blocker без секретов.
7. Никаких маркеров в sidebar, перебора чужих чатов, извлечения куки, OAuth bearer или ручной записи grant-файлов. Не маскировать отсутствие provider-structured proof зелёными unit-тестами.

## Безопасные предварительные проверки на Mac

Запускать из изолированной ветки DevOS 2, в которой имеются `node_modules`. Эти команды не требуют подключения владельческого ChatGPT-плагина:

```sh
node scripts/staging-isolation-smoke.mjs
./node_modules/.bin/tsx scripts/staging-public-mcp.smoke.ts
./node_modules/.bin/tsx scripts/staging-safe-chaos.smoke.ts
npm run build
npm test
./node_modules/.bin/tsx scripts/devos2-release-preflight.ts
```

Последняя команда при отсутствии E2E должна вернуть `blocked` с exit code **2**. Не подменять записи о реальных live-критериях произвольным `passed`: preflight проверяет независимые подтверждения и приватный backup/restore.

## Минимальный положительный live-контракт

В новой, независимо разрешённой Staging-QA задаче сохранить ссылку на **точный Project-чат**, связанную GitHub Issue/PR, объявленный заранее graph, идентификатор worker turn и время теста **в приватном Staging state**. В открытых GitHub-отчётах — только безопасные ссылки на Issue/PR и итоговые статусы, без приватных chat URL, nonce, токенов, паролей или содержимого разговоров.

**PASS выдачи разрешения** требует одновременно: `probe=issued`; реальный структурированный `api_tool.call_tool` от ChatGPT в этом ходе, совпавший с pinned resource; зарегистрированный локальной системой grant; `noop.approved=true`; один принятый шлюзом `devos_worker_report` с проверенным turn token; переход Runner к заранее объявленному следующему шагу без повторной отправки сообщения. После завершения — отзыв grant.

**FAIL / BLOCKED:** если нет HTTP 200 trusted history, возвращается 401/404, есть только текст модели, MCP-отчёт отвергнут, браузерный ход потерял однозначность или не подключён отдельный Staging plugin. Остановиться без побочных Mac-операций; сохранить unresolved state для диагностики. Никаких «успехов по аналогии» со скриптом, который подставляет синтетический ответ.

После положительного теста провести **отдельно** полный Feature / Bugfix / Assess, review/rework, Codex fallback, Web/iOS authorization, live recovery и проверенный приватный backup/restore. Только после этого допустимо обсуждать релизное решение владельца; preflight сам по себе ничего не развёртывает.

Актуальные результаты и блокеры: [Issue #150](https://github.com/EmporioBreak/DevOS/issues/150), [Issue #151](https://github.com/EmporioBreak/DevOS/issues/151), [Issue #152](https://github.com/EmporioBreak/DevOS/issues/152) и [draft PR #189](https://github.com/EmporioBreak/DevOS/pull/189).

## Дополнительная диагностика: тестовый воркер использовал MCP Production

Позднейшая **строго read-only** проверка сохранённого Staging QA-чата
(никакой повторной отправки) показала в обычной загрузке ChatGPT браузером
**GET HTTP 200** на `/backend-api/conversations/{id}`. Ответ содержал
**ровно один настоящий структурированный `devos_worker_probe`**, распознанный
строгим парсером, и сохранённое совпадение pinned resource. Старый прямой
HTTP 401 не распространяется на этот успешный браузерный GET.

Обнаружен конфликт сред: локальный pinned `devos_worker_probe` у Production
и Staging **одинаковый**, хотя публичные OAuth resources разные. Запись
одноразового запроса существует у **Production** (время записи **15:39:09 UTC**),
в Staging её нет. QA state Staging обновился в **15:39:06 UTC**.
Это сильное свидетельство, что браузерный тестовый чат вызвал **основное
Production-подключение ChatGPT**, а Staging пытался проверить его в собственной
базе и не мог выдать разрешение. Прямое криптографическое сопоставление
самого nonce с записью Production не выполнялось, поэтому это наиболее
вероятная причина, а не формальное доказательство издателя. QA process lock
теперь указывает на уже завершившийся PID: старый ход без live task owner
по правилам безопасности **невозможно авторизовать задним числом**.

Перед **любым новым** настоящим Staging worker E2E обязательно выполнить
чтение локальных установленных binding идентификаторов, **без вывода самих
идентификаторов**:

```sh
DEVOS_STAGING_ROOT=/path/to/DevOS-staging \
  ./node_modules/.bin/tsx scripts/staging-worker-app-preflight.ts
```

При текущем дублировании возвращается `blocked` с кодом
`production_tool_identity_reused` и exit `2` — **не запускать воркера**.
Нужен **отдельный реально подключённый ChatGPT MCP app для Staging** с
отличающимся installed `devos_worker_probe` resource. Подключение требует
явного действия владельца ChatGPT; нельзя перезаписывать Production
resource/pin, копировать чужой OAuth или выдавать grant вручную. Даже при
`local_identity_separate` проверка сообщает `liveChatGptAppVerified=false`:
только отдельный live ChatGPT OAuth+MCP smoke подтверждает подключение.
