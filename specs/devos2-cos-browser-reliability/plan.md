# Implementation plan — adapt CoS, retain DevOS ownership boundaries

**Issue:** #239 | **Upstream CoS SHA:** `9c9ccac195be282011a5e7c8f2ee35e64f8680b7`
**Status:** draft architecture for exact owner review; no code production swap by this document.

## Intentional deviation from CoS: workers exist only for one Issue

CoS supports reusable sleeping agents that may accept unrelated future assignments. **DevOS must NOT copy this behavior.** Main Agent is the only persistent cross-Issue project-context owner; it transfers the minimum necessary task brief into newly created worker conversations. Each approved DevOS worker identity, chat, signed MCP grant, task window/tab lease, queued command and outstanding result is scoped to exactly one `repo#issue`. A `changes_requested` loop keeps those same worker chats and grants on the SAME Issue/PR until the task is genuinely completed. Successful final Main Agent acceptance and GitHub-verified Issue `completed` cause task-local retirement: cancel pending operations under normal no-replay rules, revoke worker-specific grants/leases, **delete the verified DevOS-created worker conversations from the ChatGPT account** through broker-owned durable cleanup, detach executable routing and close only the completed Issue's browser window/tabs when safely idle. A failed/ambiguous deletion stays visible as cleanup pending, not silently archived. Unresolved ambiguous sends must never be cleaned up by declaring a false `completed`. Keep signed reports, commits, PR comments and authorized audit records; do not delete them simply to 'reset context'. A future Issue always receives new worker chats, auth grants and conversation context, even if it uses a worker ID/role string identical to an earlier Issue. There must be no 'sleeping workers pool' shared across Issues.

This is a **functional lifecycle requirement** and needs concurrency, rework, completion, late-response and cross-Issue tests. Browser **process/profile** lifetime is distinct from **worker** lifetime: the shared Camoufox process may outlive one completed Issue as long as another Issue is active, but its retired worker sessions cannot be reactivated for a different Issue.

## Worker conversation disposal (owner-approved behavior)

**Distinct lifetimes:** The shared browser process may continue serving other Issues; a particular worker chat must **not** survive an accepted/completed Issue as an account-history entry. This supersedes the former “leave historical worker conversations in ChatGPT for audit” interpretation. Keep only minimal signed **GitHub** audit artifacts and redacted deletion receipts.

**Sequence and ownership (must be one fenced task-scoped protocol):**

1. Main Agent independently accepts the exact original Issue/review round, verifies the linked PR merged if applicable, and verifies GitHub Issue closed as `completed`. A developer/reviewer result or local `completed` marker alone does not meet the gate. Failed/not_planned/paused/changes_requested tasks are not eligible for this automatic cleanup path.
2. Durably snapshot required GitHub signed MCP reports, test evidence, PR/merge SHAs, approval and trace identifiers **without storing full worker transcripts**.
3. Revoke the exact Issue's worker MCP grants, send/open/revival leases and ability to start another turn. Quiesce only its task window/tabs; ensure no live ambiguous turn or owner dispute exists. If such a turn cannot be settled, hold cleanup as `blocked` — do not resolve ambiguity by deleting evidence.
4. Broker enumerates **only exact provider conversation IDs that its own trusted creation/ownership ledger registered** under this Issue and original ChatGPT account/workspace/Project. Do not enumerate or select other chats using sidebar names, conversation history search or matching role labels; never delete the main-agent chat or Project.
5. For each bound ID, persist a durable deletion intent, claim its one destructive attempt, independently recheck account/project/conversation, then invoke the provider-supported authorized UI deletion and confirmation. Keep `prepared → armed → provider_account_deleted` or `ambiguous/blocked` state in the existing canonical broker outbox/cleanup journal, with exact attempt identity and crash-safe reconciliation. A click timeout is not negative proof and does not authorize an immediate repeat. “Account deleted” requires the exact provider confirmation/authorized verification; a missing sidebar row or closed tab is insufficient. DevOS cannot claim backend physical erasure immediately.
6. Only after every originally registered worker conversation for this Issue has a verified account-deleted outcome may task-local windows/tabs and ephemeral worker bindings be purged. Keep a minimal non-sensitive, durable cleanup receipt in the Issue record. If the browser cannot delete/verify, mark cleanup pending, surface the blocker and preserve a safe retry/reconciliation path; do not fake completion or delete a different conversation.
7. Cleanup is performed by the broker **after the worker graph has stopped**. No worker prompt can delete itself or call a generic account-wide Delete All action. Only the original task owner may explicitly authorize exceptions; no implicit bulk deletion.

This requires a dedicated end-to-end capability and consent review: the ordinary ChatGPT UI exposes per-chat Delete, but a stable public programmatic deletion API is **not** assumed. Deletion is irreversible in the account. Per OpenAI published policy, backend removal is normally scheduled within 30 days subject to retention/legal exceptions; DevOS verifies account-level removal, not provider backend destruction.

## Multi-Issue execution, resource scheduling, and owner review (first-class, owner requested)

**Concurrency ownership is at the project dispatcher, not one Runner.** Main Agent designs and explicitly approves each Issue independently. A task dispatcher then admits several approved `repo#issue` workflows and persists one scheduler record per Issue (queued, running, waiting, blocked, final_review_required, cleanup_pending, completed). Each Runner still executes **one** already approved Issue/graph; the dispatcher does not invent cross-Issue workers or bypass approval by opening another Worker chat. Main Agent need not remain actively generating while approved workers run. All state transitions and priorities are durable so a restart reconstructs the existing approved work, not new workers or duplicate submissions.

**One shared browser broker, distinct Issue namespaces:** one persistent Camoufox/profile root; independent Issue windows; exact worker tab leases; task+worker+turn command keys; exact per-chat serial Send; bounded browser operations and backpressure with a configurable **max concurrent Issues** (start conservative; no hardcoded claim of unlimited throughput). A busy/failed/blocked browser worker must release global scheduling capacity promptly except its own immutable claim/receipt. Workers in other Issues are unaffected by one job's retries, failure or cleanup. Tests must simulate A waiting, B reviewing, C blocked, crash/restart and task-only closure without cross-Issue loss or fairness starvation.

**Owner-approved worktree mode replaces shared-checkout write serialization:** maintain ONE canonical permanent Production checkout, Production connector and persistent Camoufox profile. Concurrently active code-modifying Issues each receive exactly ONE temporary, tracked worktree on their existing approved task branch/PR, within a managed bounded directory. Register exact Issue/branch/path/HEAD and process ownership before handing the workspace to its workers; the same Issue shares that one worktree across its workers. Two Issues can genuinely edit and test their own trees simultaneously without `git switch` in the Production checkout. The worktree is only an isolated Git workspace, never a second DevOS runtime, browser profile or connector. After Main Agent verifies accepted scope, reviewed PR actually merged, GitHub original Issue closed `completed`, and all task writers are safely quiesced, confirm worktree ownership, clean tracked/untracked/ignored contents and verified merge ancestry; then safely run `git worktree remove` (no `--force`) on the exact managed path, remove its proven merged local task branch, and record terminal cleanup. Do not force-prune dirty, active, unmerged, symlinked, unverified or foreign workspaces; preserve with `workspace_cleanup_blocked` and resume/reconcile after interruption. Never delete the original checkout or another Issue's tree; do not retroactively clean up #232 or legacy workspaces.

**Final review is not a global execution barrier.** Every signed `FINAL_REVIEW_REQUIRED` commits its own owner-wake event keyed by Issue and review round. The one permanent Main Agent conversation has one serialized owner-notification sender: wait while busy/generating, deliver all distinct pending Issues fairly in event order (optionally batch statuses without losing exact per-Issue receipt), and never duplicate uncertain sends. Main Agent makes one independent final acceptance decision per original Issue; if changes_requested, original worker chats remain alive for that Issue. After actual merge/verified completed, broker revokes and **deletes that Issue's chats from ChatGPT** as already specified; other Issues, pending notifications and shared browser remain untouched.

**Graduated rollout:** first prove one Issue reliability and command ledger, then two simultaneous Issues with isolated windows and scheduler, then three concurrent Issues including one stuck/reviewing and Main Agent busy, then actual verified per-Issue chat deletion. Design/code for multi-Issue from day one; don't activate parallel Production sends before independent, authorized headed E2E and owner approval.

## Architecture decision

**Do not install CoS alongside DevOS.** Its full Electron+Chrome/Edge/Brave MV3 extension + HTTP bridge would become a competing browser/process/session owner and does not directly support the existing Camoufox/Firefox profile. Instead use CoS's precise ownership, outbox, durable command ACK, broker and observation contracts to rebuild the existing DevOS browser subsystem behind its unchanged `Executor`/signed-MCP interfaces.

**One ledger, one broker, multiple adapters.** Central `BrowserCommandStore` owns durable, task+turn+document fenced commands; project `BrowserBroker` owns profile/windows/tabs; the existing `ChatGptBrowserExecutor` becomes a transport-specific adapter, initially Camoufox. Optional Chromium extension adapter is a future separately approved migration with authenticated permissions/provider terms verification; never silently migrate the profile. `owner-wakeup-ledger` (currently Draft PR #225) and shared-browser in-memory `turns` (Draft PR #227) must be **consolidated**, not stacked as independent send authorities.

## Delivery protocol

1. Admission: confirm signed DevOS Issue/worker/turn grant, saved session and project scope. Persist immutable intent with payload digest and incarnation.
2. Claim: atomic, one-time lease against current project runtime/profile/document owner. Opening/Send authority consumed *before* native side effect. Another process sees claim as blocked, not absent.
3. Observe: current verified window/tab/document/epoch, URL, editable composer, current authenticated account/protection and busy/generation status. Reject foreign/stale evidence. No tab creation based on uncertain query.
4. Perform: one native UI operation in task window. A timeout during/after click is **unknown**, not safe to repeat.
5. Receipt: exact provider-origin user-message ID + immutable conversation and matching command/prompt evidence, persisted before any ACK or UI success claim; verify assistant final separately. Missing/conflicting receipt remains ambiguous; only read-only reconciliation may settle it.
6. ACK: idempotent retrieval and bounded custody retention; processor crash never refunds spent authority.
7. Cleanup: only exact terminal-approved task window/tab, never whole shared profile while another live lease exists.

## Backward compatibility and migration

- Inventory `.devos/state/*.json`, task/browser metadata, real old Node PID/identity/socket, shared profile and all known conversations **read-only**.
- Quiesce/adopt only when every old command has a verified terminal status or preserved explicit ambiguity and no live old runtime can independently relaunch the profile. On unverifiable state refuse a second context; don't kill legacy and don't report green E2E.
- New protocol opt-in only for newly approved work. Existing #226 ambiguous turn 6 stays unchanged. Do not use a new Staging connector, cookie export, second profile or test reset.
- Migration from old per-task runtime to shared project broker must be transactional, preserving original GitHub PR/worker identity and signed MCP credentials.
- Feature flags are deploy gates, not independent second authorities; rollback must preserve spent Send/command receipts.
