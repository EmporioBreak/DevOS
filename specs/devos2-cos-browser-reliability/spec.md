# Feature: CoS-derived reliable browser workers for DevOS

**Issue:** EmporioBreak/DevOS #239
**Source benchmark:** https://github.com/totec448-spec/chat-on-steroids
**Pinned upstream:** `9c9ccac195be282011a5e7c8f2ee35e64f8680b7`
**Status:** DRAFT — not an approved original Spec Kit / worker graph; no production rollout authorized.

## Problem / user stories

DevOS workers sometimes remain stuck because the existing Camoufox runtime, worker conversation, detached process and attempted Send are observed by different owners. The model/user cannot reliably distinguish an alive process from an alive authenticated page, a pending promise from an actual provider-accepted turn, or an idle Main Agent chat from one currently generating. Repeated recovery risks two browser processes using one profile or resending a message.

- As the owner, I want DevOS to run concurrent Issues independently without assigning every worker to local Codex just because browser reliability is poor.
- As Main Agent, I want genuinely signed, final worker results, preserved PR and conversations, and exactly one task-scoped final-review wake-up for each approved review round.
- As a browser worker, I want to resume **the same** ChatGPT conversation after a crash or review correction, not start a new conversation because an unrelated tab stopped answering.
- As an operator, I want clear diagnosis distinguishing waiting on authorization, busy/generating, invalid chat/project, connection loss, lease mismatch, submitted-but-unconfirmed, completed and manually closed.
- As the user, I want browser/desktop/iOS capability claims backed by actual observations, not by running a shell command.

## Requirements (source-aligned)

FR-01 — Exact durable ownership: one canonical browser command/outbox authority per DevOS project; a command binds immutable Issue, worker, worker turn, approved graph version, profile/process owner, task window, worker tab/document/navigation epoch, conversation ID (if known), payload digest and transport incarnation. No runtime component can invent ownership from a title, tab position, hostname or repeated worker ID.

FR-02 — Durable delivery: persisted command prepared → uniquely claimed before open/Send → native action → exact provider message receipt → acknowledged. Queued, composer inserted, post-click, submitted and completed are separate facts. A lost ACK, process exit or ambiguous send **does not authorize retry**. Provider read-only reconciliation can confirm the original message; conflicting/duplicate message IDs block.

FR-03 — Browser lifecycle: one shared persistent Camoufox profile/OS browser root **per project**, one top-level window per eligible Issue, and worker tabs scoped to the correct Issue window. Only task A final approval closes A; B stays intact. Profile ownership and possible old Node process relaunch are checked before any browser launch. Preserve and safely adopt existing trusted legacy sessions without kill/reset/copied profile.

FR-04 — Issue-scoped conversation continuity: while one Issue is active, its exact worker ID resumes the same saved Project conversation (including review corrections, runtime restart, and read-only recovery). A new Issue ALWAYS receives a fresh worker identity, fresh Project conversation, fresh signed grant and zero inherited worker chat context, even if the worker has the same role/name. User-created private chats cannot be inferred through sidebar traversal. Browser user auth and MCP grant remain distinct. Revoked grant can never be inherited by a new chat.

FR-05 — Browser evidence: one bounded provider DOM adapter owns selectors and structured observations; document id + navigation epoch + exact conversation must match before any mutation. On A→B→A navigation, stale A callbacks cannot send. A tab listing error is unknown, not zero tabs. Human/active draft/safety/restriction/verification screens stop automation.

FR-06 — Worker report and review: signed MCP status is terminal authority; no fake textual status. Browser worker active generation/tool work renews a bounded wait, but page presence does not. Preserve same chats/PR on changes_requested. Main Agent alone approves. Runner graph and signed skills frozen; **do not import CoS dynamic agent spawning or account switching**.

FR-07 — Main Agent notification: one task/review-round command after durable final_review_required, exact signed owner-chat fingerprint, verified private editable original /c after /share redirect, bounded busy/idle waiting and send provider receipt; never notify while chat is active and never forge owner approval.

FR-08 — Observability/recovery: structured bounded, redacted events for ownership, claim, browser process, document, receipt and final status. Restart reconstructs only previously committed facts. Recover or reload only when a corresponding exact obligation authorizes it; manual close never causes automatic re-opening. No unbounded retry daemon/watchers.

FR-09 — Backward-compatible security: no second connector or browser profile, no credentials copied or extracted from browser, no provider protection bypass, no hidden account switch, and no automatic coercion of unknown provider API. New adapter is opt-in and must not change outstanding #214/#224/#226/#232 signed turns during rollout.

FR-10 — Worker context lifetime equals the GitHub Issue lifetime, **not** the CoS reusable-agent lifetime. Main Agent alone maintains the durable cross-Issue project context. While Issue is active/running/final_review_required/changes_requested, predeclared worker chats, task-scoped MCP grants and history remain available ONLY for rework on that same Issue. When Main Agent approves and Issue genuinely reaches completed, revoke task-scoped worker grants, stop accepting any worker sends/revival on its old task leases, close only that Issue's browser window/tabs after confirmed teardown, and retire worker conversation bindings from executable routing. Preserve necessary GitHub diff, reports, decision history and audit evidence, but never reactivate or seed a new Issue from prior worker chat history. A newly opened Issue starts with new worker conversations and explicitly scoped Main Agent-provided context; never silently copy prior worker memory.



FR-11 — **Verified physical deletion of DevOS-created worker conversations after Issue completion (owner requirement).** Not archive, hide, detach or merely close tabs. The deletion controller is the trusted DevOS broker, **never** a worker executing its own last turn. Delete only when Main Agent has independently accepted the exact Issue; its relevant PR is merged (when applicable), the original GitHub Issue has been verified closed with reason `completed`, all required signed reports/audit records have been durably retained, and no review correction, potentially active turn, ambiguity or foreign-task ownership remains unresolved. First fence all task-scoped sends/revives and revoke worker grants; then run a bounded per-conversation deletion intent/receipt workflow keyed by the exact verified DevOS-created provider conversation ID, original task, Project, account/workspace and ownership fingerprint. Every native destructive action must recheck exact current browser/account/conversation; do not discover deletion targets from sidebar title/search, worker role string, Project-wide lists or URL guesses. A delete timeout is **ambiguous** and must not cause an uncontrolled second click; reconcile with authoritative read-only evidence before retry/confirmation. Remove only that completed Issue's worker chats and local transient bindings after individually verified provider/account deletion. Preserve GitHub commits/reports and audit **metadata** without copying entire chat transcripts into project storage. Never delete Main Agent's conversation, manually created chats, unrelated Issue chats, Project, or the shared Camoufox profile. If deletion cannot be executed or verified, surface `cleanup_pending`/`cleanup_blocked`, retain minimum protected cleanup metadata and do not claim complete cleanup.

FR-12 — **Truthful deletion semantics.** “Deleted from ChatGPT account” requires an observed authorized deletion confirmation for the exact conversation, not the absence of a sidebar row (which may mean archived/filtered/offline). Permanent erasure from OpenAI backend is governed by provider retention policy, not guaranteed instantly by DevOS. Never label account-level deletion as verified backend erasure.

FR-13 — **Multiple concurrently active GitHub Issues** (owner-requested core feature, not a later plugin). A project-level dispatcher may run multiple independently approved, one-Issue Runner executions concurrently without depending on the Main Agent chat remaining open. Each active Issue maintains separate immutable workflow/graph digest, worker chat identities and grants, per-Issue status, journal command namespace, review rounds, GitHub Issue/PR and task window. The dispatcher must never merge different Issues into one worker graph or reuse a worker conversation across them. A waiting/busy/blocked Issue must not stall another eligible Issue. Dispatch only fully owner-approved tasks; preserve explicit dependencies and owner-set priority. An idle Main Agent does not grant additional execution authority.

FR-14 — **Backpressure, resource isolation and fairness.** One shared project browser broker may serve bounded parallel Issue windows/tabs within the single approved Camoufox profile/process, with configurable limits on concurrent Issues, browser turns and resource consumption; excess tasks remain in a durable waiting queue rather than launching duplicate browser processes. One active mutating turn per exact worker conversation; no cross-Issue Send, tab action, MCP grant, ownership inference or cleanup. A task's retry/crash/quarantine cannot hold a global lock while the browser broker processes unrelated Issues. Fail closed on unknown/ambiguous browser ownership; preserve task-local bounded recovery. **Managed parallel Git worktrees, now explicitly authorized:** for EACH managed target repository, preserve its own long-lived base checkout while independent code-writing Issues receive one temporary managed Git worktree on their task-approved branches, so edits/build/tests may occur in parallel. DevOS itself has one permanent Production runtime checkout; this does NOT limit other target projects to that same Git checkout. Workers of one Issue share its tree. Bound allocation to project concurrency limits and durable task/path/branch ownership. A per-Issue exclusive lifecycle lease guards against duplicate tree creation/removal. Worktrees do NOT launch a second connector, Camoufox profile or Project runtime. On independently confirmed Main Agent acceptance, PR merged and Issue closed `completed`, remove only the clean, inactive, verified task-owned worktree and proven merged task branch; otherwise keep it and report cleanup blocked.

FR-15 — **Concurrent final-review wake-up without lost signals.** Each Issue independently persists its own `FINAL_REVIEW_REQUIRED` event and owner notification keyed by `repo#issue#reviewRound`; the single Main Agent chat is a serialized notification destination. If several Issues finish together or the Main Agent is composing/generating, enqueue, deduplicate and fairly deliver one authorized user-role wake-up event per outstanding review round (or a verified lossless digest containing all referenced Issues). Never spoof a provider `system` role; no automatic owner approval. Main Agent reviews each original Issue/PR separately; `changes_requested` returns to its same worker chats while other Issues continue. After an Issue is merged and closed completed, delete only its own verified worker chats using the irreversible cleanup ledger; B/C remain alive, with one shared Camoufox process.

FR-17 — **Reusable cross-project workspace management, not hardcoded DevOS self-development.** DevOS is the control plane for many independently configured GitHub repositories/projects (e.g. StoreFront, iOSApp, DevOS itself). Every managed project has a verified repository identity (GitHub owner/repo, canonical remote, trusted Git root), an owner-approved integration/base branch and its own persistent base checkout, worktree ownership inventory, resource limits, sealed tasks, worker conversations and project-scoped browser/ChatGPT authorization namespace. Temporary worktree identity MUST be `project/repo + issue + approved task branch`, never a global Issue number or role name. Worktree operations use that project's configured paths and permissions, not an embedded `EmporioBreak/DevOS` path or fixed production branch. Multiple projects may run concurrently without mixing branch pointers, files, worker chats, project profiles, credentials or cleanup state. Existing DevOS Production connector/runtime remains a control-plane singleton; other projects' base checkouts do not become additional DevOS MCP/Production installations. One browser runtime per independently authorized project/tenant context, or approved equivalent isolation, not one unsafe global profile shared by unrelated accounts.

FR-18 — **Universal self-cleaning owned resources across projects.** Maintain a durable per-project resource ownership registry for DevOS-created task worktrees, branches, task-local child processes and temporary outputs, tied to exact original Issue/PR/project. Only DevOS-managed resources with verified identity are deletion candidates; unknown/pre-existing user worktrees must never be discovered and force-pruned just because they look stale. On successful final acceptance, target project PR merge into its approved base branch and verified Issue closed `completed`, perform task-scoped idempotent worktree cleanup, safely deleting its merged task-local branch and removing its registry entry only after verified filesystem/Git removal. On crashes, unclean content, lost permission, unmerged commits, ambiguous Send or active task use, retain resources as `cleanup_blocked` and surface an actionable diagnostic with exact project/task. Periodic reconciliation is bounded and read-only first, reconstructs known managed worktrees and offers safe cleanup only after the same strong completion/ownership checks. A Project A cleanup must never enumerate, remove, prune, or modify Project B. There is no accumulation of zombie worktrees for successfully completed tasks.

## Acceptance examples

A. Two independently signed Issues have distinct window leases, worker tabs, conversations and MCP grants within one Camoufox profile/process; cleanup A cannot remove B.
B. Crash at each prepared, claimed, post-click, provider-receipt and post-ACK boundary is safe; at most one native Send **attempt** per exact command ID, even after restart.
C. User message ID and exact conversation ID match the originally claimed command before reporting sent; provider final/result is independently observed, not derived from a click.
D. Multiple changed browser tabs, including A→B→A, stale callbacks, same worker names, overlapping review turns and user-closed tabs never cross ownership.
E. Saved ambiguous turn 6 of #226 is preserved; new logic cannot replay it or launch a second profile. Verified read-only recovery or explicit irrecoverable blocker is visible.
F. Main Agent busy → notification stays pending; original private writable chat verified → one message; after ambiguity → no duplicate; changes_requested makes a new review round, not a new worker chat.
G. Real headed Production ChatGPT E2E, independent security review, full build/tests; a mocked Playwright case does not substitute.
H. On changes_requested for Issue A, same declared worker resumes the same A chat; after A is genuinely completed, its grants and execution routes are retired, only A's window is closed, Issue B's browser context remains intact, and Issue C (even with the same role names) starts with entirely fresh worker conversations, grants and input context. Old A audit artifacts remain readable but never grant a new turn.
I. Completed Issue A's **actual DevOS-created** worker chats are deleted from the authorized ChatGPT account (not archived), one exact conversation at a time, with real deletion evidence. A before approval or changes_requested, foreign Issue B, owner/user chats and manually created chats are never deletion targets. Crash before/after deletion, lost acknowledgement, wrong account/project and repeated cleanup invocations cannot cause cross-chat deletion; provider/backend retention is reported accurately.

J. Launch three different **owner-approved** Issues simultaneously: A sends/reviews, B waits for a ChatGPT reply, C is blocked on one task-scoped step. B/C do not delay A, do not inherit one another's MCP permissions, and restart reconstructs the exact per-Issue scheduled/active status with zero duplicate worker sends.

K. A and B concurrently reach `FINAL_REVIEW_REQUIRED` while Main Agent is busy: preserve both notifications, dispatch each once to the one authorized owner conversation when it is ready, and never mix their approval decisions. A changes_requested resumes its existing Issue-only developer/reviewer chats; B can finish and delete only B's worker chats without interrupting A/C.

L. Two owner-approved coding Issues have separate managed temporary Git worktrees and task branches; they modify/build/test in parallel without changing the permanent Production checkout. Their browser workers still share one Camoufox process/profile.
M. After task A is approved, its PR merged and original GitHub Issue closed completed, broker removes A's clean inactive task-owned worktree and merged local branch, without touching running task B. On dirty/unmerged/in-use A, cleanup blocks and preserves files rather than forcing deletion.

N. Two unrelated repositories both run Issue #42 at the same time, with separate approved `main`/integration branches, task worktrees and worker auth. The exact same Issue number and worker role in both must never collide in registries or cleanups.

O. After a merged/completed task in Project A, only its previously registered worktree/branch/transient resources disappear, while Project B's active worktrees, different base checkout, browser worker chats and original user workspaces remain. Reconciliation after a broker crash removes only provably owned, safe-to-clean leftovers and reports an explicit blocker for dirty/unmanaged resources.

## Explicit non-goals

- Installing CoS Electron app as a second DevOS orchestrator.
- Loading its Chrome/Chromium MV3 extension into Firefox/Camoufox as-is.
- Circumventing provider automation policies, restrictions, model access, rate limits or auth gates.
- Automatically transferring ChatGPT session cookies or recording arbitrary private chats.
- Changing #232, retiring #214, silently modifying #224/#226 PRs, or reopening possibly submitted prompts.
